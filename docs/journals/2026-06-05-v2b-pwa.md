# 2026-06-05 - v2b: PWA packaging (Serwist)

Made the vault an installable PWA that precaches the static build: installable +
faster loads + supply-chain pinning (the served JS is cached locally, not
re-fetched each load). Brainstorm -> plan -> cook -> review -> commit on
`origin/dev` (`a669ea0`). PACKAGING ONLY - not offline vault access.

## What
- `app/sw.ts` (Serwist): precache `self.__SW_MANIFEST` (47 build assets) + a
  NetworkFirst rule for navigations ONLY. No runtime rule for Supabase/APIs, so
  auth/vault traffic always hits the network and is NEVER cached.
- `next.config.ts`: wrapped with `withSerwistInit` (SW disabled in dev), CSP
  preserved + `manifest-src 'self'` added.
- `app/manifest.ts` + icons generated from the vault-cube SVG (192/512/maskable +
  apple-icon) via `scripts/gen-icons.mjs` (sharp); `viewport.themeColor`.
- `components/pwa-update.tsx` (`@serwist/window`): registers `/sw.js`, shows a
  "new version, reload" toast; `skipWaiting: false` so an open vault session is
  never refreshed out from under the user.
- `public/sw.js` is a build artifact -> gitignored.

## Honest scope (recorded in the plan)
PWA does NOT give offline vault access - data lives in Supabase and unlock needs
network, so offline only loads the app shell/lock screen. True offline-vault
(cache ciphertext + offline unlock) is a separate, larger feature.

## Decisions
- Serwist over next-pwa: modern Workbox successor, Next 15 App Router-native, lets
  us hand-write a minimal SW (control) while it injects the precache manifest.
- skipWaiting:false + a reload prompt (not auto-update): security fixes still land
  fast, but the user controls the refresh.
- Supply-chain caching is double-edged (a bad cached build persists until the SW
  updates) - mitigated by the update prompt and a minimal SW.

## Review caught one edge case (fixed)
With `clientsClaim: true`, the first-ever install fires `controlling` (controller
goes null -> SW), which would trigger an unprompted one-time reload flash. Fixed by
reloading ONLY when the user clicked "Tải lại" (an intention flag), never on the
first-install clients.claim(). Also added an invariant comment: the shell HTML must
stay user-agnostic so the NetworkFirst nav rule can never cache per-user data.

## Verification
`tsc` clean, `guard` clean, `build` passes; `public/sw.js` generated with 47
precache assets and NO Supabase origin; the CSP header still emits after the wrap
(curl, includes manifest-src); `/manifest.webmanifest` + `/sw.js` resolve 200.
Install / offline-shell / update-prompt require a real device on a production build
(SW is disabled in dev) - handed to the user as a checklist.
