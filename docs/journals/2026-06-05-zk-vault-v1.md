# 2026-06-05 - ZK Credential Vault v1

Built v1 of a single-user zero-knowledge credential vault (Next.js + Supabase)
end-to-end via brainstorm -> plan -> cook. Six phases, all completed, reviewed,
and verified live. Pushed to `origin/dev` in 11 conventional commits.

Plan: `plans/260605-1204-zk-credential-vault/`.

## Key decisions

- **Hash != storage (corrected up front).** The original ask was "use hashing to
  store data." Hashing is one-way; credentials must be retrievable. Went with
  **envelope encryption**: Argon2id KDF -> KEK, random 256-bit DEK encrypts items
  (AES-256-GCM), DEK wrapped by both a master-KEK and a recovery-KEK. Changing
  the master only re-wraps the DEK; items are never re-encrypted.

- **Email-derived auth salt (solved a chicken-and-egg).** Mid-build realized
  cloud ZK auth is circular: to read your encrypted config you must authenticate,
  but the auth salt lived inside that config. Fixed Bitwarden-style:
  `authSecret = Argon2id(master, salt = SHA-256(email))` with a fixed `AUTH_KDF`
  cost, so login needs no prior DB read. Removed `saltAuth` from stored
  `KdfParams`. KEK salts stay random in the DB.

- **Recovery = Option A (export file), RLS stays strict.** The recovery key
  decrypts a self-contained encrypted `.vault` export; no anonymous cloud read.
  Lost master -> create new vault -> import old file with the recovery key
  (decrypt-then-re-encrypt under the new DEK).

## Bugs caught by review (both could brick a vault silently)

- **Recovery-KEK normalization asymmetry.** `createVault` derived the recovery
  KEK from raw `words.join(" ")` while unlock used the normalized phrase. They
  matched only by luck of the English wordlist; any drift would have made the
  recovery wrap permanently un-unwrappable. Fixed: normalize (NFKD) on both paths.

- **change-master brick window + false "reverted".** Blind rollback after an auth
  update failure could leave auth and wrap out of sync (neither password works)
  while telling the user it was reverted. Fixed: probe real server auth state
  (sign-in test old vs new), converge to a consistent pair, and never claim
  "reverted" unless verified. The recovery key (untouched by change-master) is the
  documented escape hatch.

- **Import hardening.** Made atomic (decrypt-all-in-memory before any write, so a
  wrong key/corrupt item aborts cleanly) and idempotent (upsert by original id, so
  a retried partial import never duplicates).

## Verification

- Live engine smoke test against Supabase: 8/8 (`npm run verify:supabase`).
